# EDAI2 E-commerce LLM Platform Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Build and prove an English e-commerce support and drift-analysis platform on GKE that earns every compatible Sheet3 point, consumes the Section 03 drift contract, and never reports more than 99/100 because the Ansible-on-VM point is deliberately excluded.

**Architecture:** Eight project-owned, effective-dated Markdown source files are chunked and embedded by an Airflow candidate-index pipeline, registered in DataHub, and served through Feast backed by PostgreSQL/pgvector. Two independent FastAPI -> streamable-HTTP MCP -> kagent `SandboxAgent` paths expose knowledge retrieval and customer-order drift detection. `CommerceAgentCoordinator` is a thin FastAPI safety/experiment/route-hint facade that calls one of three internal coordinator runtime variants through a facade-only agentgateway A2A credential: `v1-primary`, `v2-primary`, or `v1-comparison`. Those three SandboxAgent resources are versions/variants of one logical coordinator identity, and each alone can call the two specialists through a different coordinator-only A2A credential. Thus the public design still has exactly three logical sandboxed agents while making agent and model A/B assignments executable. kagent 0.9.9 runs the Go declarative agents on Agent Substrate 0.0.6 gVisor actors, while agentgateway 1.3.1 governs model, MCP, and A2A traffic to self-hosted Qwen models through the llm-d CPU router. All application and supporting services run on a small zonal GKE cluster; Terraform owns cloud resources, Helm owns application/supporting releases, and pinned llm-d v0.7 Kustomize overlays own inference because the current llm-d Helm path is deprecated.

**Tech Stack:** Python 3.12, uv, FastAPI, Pydantic v2, MCP, Feast, PostgreSQL/pgvector, Valkey, Redpanda, Airflow, DataHub/OpenSearch, BAAI/bge-small-en-v1.5, Qwen/Qwen2.5-1.5B-Instruct and Qwen/Qwen2.5-0.5B-Instruct, llm-d v0.7 CPU, kagent 0.9.9 CRDs (`kagent.dev/v1alpha2`), Agent Substrate 0.0.6, agentgateway 1.3.1, Kubernetes Gateway API 1.5.0, agentregistry/arctl 0.3.3, GKE, Terraform, Helm, Kustomize, KEDA, Jenkins/rootless BuildKit, Trivy, Crane, Vault, External Secrets, ingress-nginx, cert-manager, Prometheus, Loki, Tempo, Grafana, Grafana Alloy, Langfuse v3/ClickHouse/GCS, pytest, Hypothesis, CrossHair, mutmut, Locust, Playwright, PlantUML, and SHA-256.

## Current State, Gaps, Non-Goals, and Dependencies

- `deliverables/04.2_llm_design.md` is an explicit placeholder and says no LLM application or retrieval pipeline exists.
- The repository has reusable generator, Kafka, lakehouse, Spark/Flink, Airflow, DataHub, feature-table, evidence-manifest, documentation, and SHA-256 patterns. Python runtime is 3.12 and commands use uv.
- Existing features are `feat_customer_90d`, `feat_stream_60m`, and `feat_customer_unified`; they use `customer_id`, `event_timestamp`, feature columns, and `created`.
- There is no FastAPI/MCP service, LLM package, Feast repository, GKE/Terraform, Helm app chart, Jenkins job, Vault deployment, kagent, Agent Registry, llm-d, Langfuse, or EDAI2 evidence today.
- No planned benchmark, screenshot, cluster, deployment, UI, TLS route, or generated report is treated as existing evidence.

### Gaps this plan closes

- Add explicit API/MCP/data contracts before runtime code.
- Add candidate-index governance and atomic promotion/rollback instead of writing directly to an active index.
- Add a read-only Section 03 adapter for exact `id,label` and point-in-time features.
- Add self-hosted CPU inference, sandboxed agents, registry publication, KEDA proof, A/B assignment, and deterministic safety.
- Add GKE-only IaC, cost controls, secrets, CI/CD, observability, ingress, evidence capture, and reviewer navigation.

### Non-goals

- Production SLA/HA certification, multi-region recovery, production customer traffic, real PII, financial transactions, action-taking agents, GPU inference, model training/fine-tuning, more than eight knowledge sources, multilingual support, or a third agent path.
- Replacing the existing local Compose data-platform evidence. EDAI2 may consume its contracts/artifacts, but all EDAI2 runtime proof comes from GKE.
- Ansible, Compute Engine VMs, Cloud Build, persistent public IPs/load balancers, or secret payload migration into source control.

2. GCP project, billing account, budget notification target, DNS-capable public egress, and permissions for GKE, Artifact Registry, GCS, KMS, IAM, and Billing Budgets must be supplied outside Git.
3. Immutable chart/image/model revisions are pinned in repository manifests. `latest`, mutable model aliases, and unpinned remote Kustomize bases fail static tests.

## Typed Interfaces and Contracts

All timestamps are timezone-aware UTC. Pydantic uses `extra="forbid"`; API error bodies are `ApiError(code: str, message: str, request_id: UUID)` and never include secret values or raw PII.

### Trusted-source grammar

Each of the eight UTF-8/LF/no-BOM files ends in one newline and contains one or more records in this exact grammar; unknown/missing keys or free text outside a record fail parsing:

```text
---
document_id: <stable kebab-case ID>
category: <one KnowledgeCategory value matching the filename>
version: <SemVer>
effective_from: <RFC3339 UTC timestamp>
effective_to: <RFC3339 UTC timestamp or null>
---
<canonical Markdown body>
```

Seven files contain one current record. `returns.md` contains exactly two records separated by the line `<!-- version-separator -->`, giving eight logical documents/files but nine document-version records. Its records have the same `document_id` and category, distinct versions, and adjacent non-overlapping intervals where historical `effective_to == current effective_from` and current `effective_to` is null. Every other record also has a null end. The parser requires 300-700 words in every single-record file and 150-350 words in each returns record, rejects duplicate `(document_id, version)`, an interval gap/overlap, malformed delimiter/front matter, category/filename mismatch, noncanonical encoding/newlines, and content outside the word bounds. `source_sha256` hashes the canonical raw file bytes; per-version content hashes cover the canonical Markdown body bytes. Chunking occurs independently inside each version, never across the separator.

```python
from datetime import date, datetime, timedelta
from enum import StrEnum

def require_utc(value: AwareDatetime) -> AwareDatetime:
    if value.utcoffset() != timedelta(0):
        raise ValueError("timestamp must be timezone-aware UTC")
    return value
```

### Behavioral invariants

- `effective_at=None` resolves to request time. Eligible chunks satisfy `effective_from <= effective_at < effective_to`, or have a null `effective_to`; overlapping versions for one document fail candidate validation.
- Chunking normalizes body text to Unicode NFC, loads `AutoTokenizer` for the pinned BGE revision with `add_special_tokens=False`, and creates token-ID windows at starts `0, 320, 640, ...`; each window contains at most 400 tokens, the final nonempty window is retained, and overlap is exactly 80 tokens whenever a successor exists. Each row stores tokenizer model/revision, ordinal, token start/end, decoded canonical content, and its SHA-256. `chunk_id` is SHA-256 over UTF-8 RFC 8785/JCS canonical JSON `{document_id, version, ordinal, token_start, token_end, content_sha256, tokenizer_revision}` rather than ambiguous concatenation. Promotion is a compare-and-swap of one active alias; candidate rows are immutable.
- BGE passage embeddings encode the canonical chunk text with no prefix; query embeddings encode the exact string `Represent this sentence for searching relevant passages: <query>`. Both use the pinned model/revision, `normalize_embeddings=True`, and reject a non-384 or non-finite vector. PostgreSQL stores `embedding vector(384)` and performs an exact pgvector cosine scan with `<=>` because the nine-version corpus is deliberately small; no HNSW/IVFFlat approximation is allowed in this coursework profile. Apply category and `effective_from <= effective_at < coalesce(effective_to,'infinity')` filters before distance, then order exactly by `embedding <=> query_vector, chunk_id` and take `top_k`; expose `score = 1.0 - cosine_distance` without reranking. The Feast retrieval service calls this one adapter; contract tests byte-compare its ordered IDs/distances/scores with direct adapter results on the same tie fixture.
- Grounding is route-specific. For support, the verifier reloads each knowledge chunk by ID/hash and requires every factual sentence to be an exact normalized statement supported by at least one cited chunk. For drift, it canonicalizes the successful tool-result JSON excluding transport metadata, verifies `result_sha256`, the strict Section 03 manifest hash and named feature-health artifact hash, and permits only claims entailed by the bound feature/value/status/dates. Drift claims use `DriftEvidenceCitation`, never a fabricated knowledge chunk. An absent citation, wrong citation kind, hash mismatch, altered value, or unsupported sentence deterministically replaces the answer with an abstention; raw generation is retained only in redacted Langfuse telemetry.
- The selected pinned Qwen tokenizer counts the fully rendered chat template. Reserve exactly 128 of the 4096 tokens for generation, so serialized system prompt + tool schemas + retained complete history turns + whole evidence records + current user message must be at most 3968 tokens. Reduce over-budget input deterministically by dropping the oldest complete history turn group first (including its assistant/tool messages), then the lowest-score retrieval chunks in `(score, chunk_id)` order; never split a turn, truncate a chunk, or invalidate its content hash. System/tool schemas and the current user message are fixed. If those fixed fields still exceed 3968, return HTTP 422 with `ApiError.code="context_too_large"` and do not call an agent/model. If all evidence is dropped, return a grounded abstention rather than an ungrounded answer. OTel/Langfuse record tokenizer/revision, pre/post token counts, and dropped turn/chunk IDs—but no dropped raw text.
- Section 03 ingestion is fail-closed and idempotent. `load_section03.py` first strict-verifies a manifest whose `runtime_evidence.status` is `verified`, every named artifact/hash, schemas/counts/cutoff, and source configuration hash. Under a PostgreSQL advisory lock it `COPY`s training and health rows into immutable tables suffixed by the manifest SHA-256, rejects any mismatch, and transactionally repoints `edai2_section03_training_active` and `edai2_section03_health_active` views. It then runs `feast apply` and materializes the customer snapshot to Valkey. A repeated active hash is a no-op only when SQL/registry/online fingerprints match; a Feast failure restores the prior views and rematerializes the prior version. The loader emits before/after hashes, row counts, Feast registry/online fingerprints, and rollback status without changing Section 03's exact `id,label` artifact.
- The Section 03 adapter maps `id` to Feast entity keys without changing the source schema and performs an `event_timestamp <= as_of` point-in-time join against `ml_customer_purchase_training`; it registers `agg_feature_health_daily` as the population drift source. The drift API cannot become Ready until the imported active manifest hash equals the strict prerequisite hash.
- MCP tool schemas are byte-compared with the matching OpenAPI component schemas. Timeouts are 700 ms retrieval, 1.5 s drift, and 22 s chat; one retry is allowed only for idempotent connection failures with jittered backoff. Timeout returns a typed abstention, never fabricated data.
- Agent and model experiments are independent and target deployed resources. `coordinator-v1-primary` and `coordinator-v2-primary` are two runtime versions under the single published `commerce-coordinator` identity; support/drift specialists, tools, primary ModelConfig, index, safety code, and timeouts are identical. V1 says to answer concisely and cite every factual claim; v2 changes exactly one system-message field to call the selected evidence tool first, bind each factual claim to returned evidence, and abstain when binding fails. Assignment uses `sha256("agent_exp_v1:" + session_id) % 100` with 0-89 routed to `v1-primary` and 90-99 to `v2-primary`; evidence deterministically selects UUIDs until each arm has 60 observed sessions. Model evidence uses the independent salt `model_exp_v1`, routing `v1-primary` versus `v1-comparison`; those resources have identical prompt/specialist/tool/index/safety hashes and differ only in primary/comparison ModelConfig/model digest. Telemetry records exact A2A destination, coordinator runtime, ModelConfig/model digest, assignment, every held-constant revision, and proves no session switches arms.
- `TimeWindow.start < TimeWindow.end` and every timestamp must pass the timezone-aware UTC validator. `baseline_window` must equal the seven complete UTC days ending on the Section 03 `baseline_date` (`00:00:00Z` six dates earlier through that date's inclusive end, represented by an exclusive next-midnight API end). `candidate_window` selects 1-30 complete monitoring dates beginning after `baseline_date` and stays within the published health range. The service reads the fixed baseline distribution metadata and all selected candidate health rows from Feast, returns the candidate row with maximum `(psi_vs_baseline, monitoring_date)` as the deterministic peak, sets status from exact 0.10/0.15 thresholds, and exposes `window_days=7` plus the fixed cohort size. Optional `id` only enriches the population result with the latest cutoff-safe Section 03 feature/label row; it never changes PSI.
- Missing active index/health data returns HTTP 409 `index_unavailable|feature_unavailable`; dependency timeout returns HTTP 503 `dependency_timeout`; invalid windows/IDs return HTTP 422. These responses use `ApiError`. Chat converts them to a recorded failed/timed-out `ToolCallRecord` and an abstention, so no fixed response field is fabricated or filled with `NaN`.
- `ChatRequest.route="auto"` invokes `RouteStrategy`; an explicit specialist route bypasses classification but never bypasses authorization, injection/PII checks, tool-schema validation, or grounded-response verification. Every attempted MCP call appears once in `tool_calls`, including failures and timeouts; `claims[].citations` is the response citation contract.
- `GET /healthz`, `GET /readyz`, and `GET /metrics` are part of every FastAPI OpenAPI contract. Health proves process liveness, readiness verifies only that service's required dependencies, and metrics are Prometheus text format without PII labels.

### Feast streaming-writer contract

The existing Kafka bootstrap provisions `customer_feature_updates.v1` and `customer_feature_updates.v1.dlq` with one partition, replication factor one, `cleanup.policy=delete`, and seven-day retention. The strict Section 03 loader is the bounded producer: after successful view activation it inserts a transactional PostgreSQL outbox in ascending `id,event_timestamp` order as canonical JSON, with `event_id = UUIDv5(EDAI2_NAMESPACE, manifest_sha256 + ":" + id + ":" + event_timestamp)` as the primary key. A dispatcher locks pending rows, publishes that stable event ID, and records broker partition/offset only after acknowledgement; acknowledged rows are immutable. A repeated manifest first proves the complete expected event-ID set is already acknowledged and becomes a no-op, so new broker offsets cannot create duplicates. `infra/kafka/schemas/customer_feature_updates-value.schema.json` is a Draft 2020-12 schema with `additionalProperties=false` and requires `event_id`, `id`, UTC `event_timestamp`, UTC `created`, `feature_service_version`, the nine exact `Section03FeatureRow` feature values excluding `label`, and `source_manifest_sha256`; it also defines the redacted DLQ envelope.

Both writers consume `customer_feature_updates.v1` but use independent consumer groups and never share offsets. They validate the exact JSON Schema before mapping a record; each invalid input therefore creates one deterministic DLQ record per group, keyed by `UUIDv5(EDAI2_NAMESPACE, event_id + ":" + consumer_group)` and containing only DLQ ID, event ID, consumer group, source hash, schema version, and redacted reason metadata.

- `edai2-feast-offline-v1` transactionally upserts PostgreSQL by `(id, event_timestamp, feature_service_version, event_id)` and stores the Redpanda partition offset in the same transaction. Duplicate `event_id`/offset is a no-op; the consumer commits only after the database commit.
- `edai2-feast-online-v1` writes through the declared Feast PushSource to Valkey, records `event_id` plus destination fingerprint in the PostgreSQL dedup/checkpoint table, and commits only after Feast acknowledges. Retry uses the same event ID and cannot regress a newer entity event timestamp.

Writer readiness requires the mounted/configured repository JSON Schema hash to equal the hash in `streaming/bootstrap.json`, access to both pre-provisioned topics, and access to its own destination; there is no Schema Registry dependency. The combined smoke publishes one deterministic fixture plus a duplicate and one malformed fixture, then proves one effective row/value in each destination, one checkpoint advance per group, zero duplicate effect, and exactly two redacted DLQ records distinguished by consumer group. Each offline/online Jenkins job filters and proves exactly its own single DLQ record and distinct destination/checkpoint, so the jobs remain independently scoreable.

### Trial-budget envelope

`configs/gke/cost_envelope.yaml` fixes: trial credit `$300`, Terraform budget `$240`, pre-deployment forecast ceiling `$180`, regular-platform node-hours `<=96`, aggregate Spot node-hours `<=72`, second-Spot-node hours `<=16`, public-ingress hours `<=24`, evidence-session TTL `<=6h`, balanced persistent disk `<=80Gi`, and combined GCS/Artifact Registry storage `<=15Gi` over the 90-day trial. `$60` remains outside the Terraform budget and another `$60` inside it remains forecast reserve.

`check_budget.py` snapshots current us-central1 Compute, Spot, disk, GKE, registry, GCS, KMS, and ingress SKUs, reads the profile manager's hash-chained node/storage/ingress usage ledger, and requires a user-supplied current-spend value copied from the Cloud Billing console within 24 hours (the screenshot is evidence, not parsed as authority). It calculates worst-case remaining cost from unused caps and fails closed when projected total exceeds `$180`, either ledger estimate or console spend reaches 75% of the `$240` budget, the two values differ by more than `$5`, the trial expiry is less than the requested TTL, or inputs are stale. The 50% alert triggers review; 75% blocks all profile entries except suspend/backup; 90% and 100% trigger immediate suspend and prohibit resume. Budget alerts are notifications, not enforcement; these profile gates are the enforcement path. This avoids adding BigQuery billing export outside the approved GCP service list.

Every `core`/`rubric-evidence` transition requires `--ttl` (maximum 6h), writes the expiry to the run manifest, and creates a Workload-Identity auto-suspend Job. A hash-bound evidence-session lease in PostgreSQL stores owner run ID, commit, expiry, phase, and active child-job refcount. The outer six-job trigger acquires the sole lease, and each Jenkins job registers/releases only its child reference and performs release-local cleanup in `post { always }`. With the explicit `--handoff-lease-to-evidence` mode used in Task 9, the outer trigger may compare-and-swap ownership from its CI run ID to the parent evidence run only after all six jobs are terminal, the refcount is zero, evidence hashes are durable, and commit/expiry are unchanged; this success handoff keeps the profile for Tasks 10-11 without creating a second lease. Without a valid handoff—or after a failed CI wave is recorded—the outer trigger disables ingress and requests `suspended`. Task 11 explicitly releases the handed-off lease and suspends; Task 12 must pass a fresh budget gate and acquire a new lease before resuming. A standalone job may suspend only when it acquired the sole lease itself; the TTL auto-suspend is the crash fallback. Because Standard-node compute is billed separately and Spot prices change, no hard-coded dollar estimate is accepted as evidence; the live forecast and fresh Billing-console observation are authoritative inputs. The single zonal cluster management fee is expected to be offset by the applicable monthly credit but is still included in the live check if the credit is unavailable.

Recovery order is Vault/KMS -> PostgreSQL/Valkey/Redpanda -> Feast/Airflow/DataHub -> verified GCS model cache -> llm-d router/models -> MCP/APIs/agents -> observability/ingress. Rollback order is route traffic away -> `rtk helm rollback` app -> restore prior ModelConfig/model digest -> compare-and-swap active index alias -> smoke/evaluation gate. GCS stores encrypted backups/evidence and Airflow logs; the non-secret persistence fingerprint covers PostgreSQL schemas/rows, Feast registry and Valkey online keys, Substrate Valkey state, Redpanda watermarks and group offsets, ClickHouse/Langfuse trace IDs/count, OpenSearch/DataHub indexed URNs/count/hash, Agent Registry versions, Jenkins jobs, Vault canary metadata, PVC identities, GCS object generations/hashes, and one recent Prometheus/Loki/Tempo sample within retention. No secret-bearing Vault snapshot is committed.
